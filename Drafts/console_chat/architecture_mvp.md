# Архитектура консольного чата — минимальная версия (MVP)

Это **копия полной архитектуры**, из которой вырезано всё, без чего система сможет выполнять
самые базовые функции: **создать чат и обмениваться сообщениями**.

Исходная полная версия: **[architecture.md](./architecture.md)**.

---

## 1. Что осталось (максимально тонкий вариант)

Базовые функции, которые обязаны работать:

- Регистрация и вход пользователя.
- Создание чата.
- Отправка текстового сообщения.
- Получение истории сообщений.

Для этого хватает **одного процесса** (`ChatService`), который совмещает аутентификацию и чат.
Отбрасываем: отдельный `UserService`, `API Gateway`, RabbitMQ, WebSocket-hub, роли, профили, outbox.

---

## 2. Урезанная схема

```
ConsoleClient (консоль)
        │  REST (HTTP)
        ▼
  ChatService (ASP.NET Core, один монолит)
  ├─ Chat/User ApplicationService
  ├─ Domain (Chat, User, Message)
  ├─ EF Core Repository + UnitOfWork
  └─ PostgreSQL (одна БД)
```

Диаграмма деплоймента превращается в два узла: **клиент** и **один сервер с одной БД**.

---

## 3. Урезанная доменная модель

Остаются только сущности, нужные для хранения и обмена сообщениями:

- `User` (id, username, passwordHash) — без профиля и ролей.
- `Chat` (id, name, ownerId) — без ролей участников: любой участник = просто пользователь.
- `Message` (id, chatId, authorId, content, sentAt).
- `MemberRole` — **удалён** (роли не нужны для базовой работы).

Модель событий, value objects (`ChatName`, `UserProfile`), enum ролей — **убраны**.

---

## 4. Урезанный прикладной слой

- Команды остаются: `CreateChat`, `JoinChat`, `PostMessage`, `GetHistory`.
- Порты: `IChatRepository` (+ доработка `IUserRepository`) и `IUnitOfWork`.
- **`IMessageBroker` удалён** — сообщения доставляются напрямую из repositroy/команды, без шины.

---

## 5. Что удалено (список) и почему

| Компонент полной версии | Удалено? | Причина |
|------------------------|:--------:|---------|
| `API Gateway` | ✅ | Запросы идут сразу в один ChatService |
| `UserService` (микросервис) | ✅ | Аутентификация живёт в ChatService |
| `RabbitMQ` + `IMessageBroker` | ✅ | Нет кросс-сервисных событий; доставка прямая |
| `WebSocket/SignalR Hub` | ✅ | Новые сообщения получаются опросом (polling) или в цикле входа |
| Outbox-паттерн | ✅ | Нет шины, не нужна гарантированная очередь |
| Роли (`OWNER/ADMIN/MEMBER/GUEST`) | ✅ | Для базовой работы достаточно «участник/владелец» |
| `UserProfile`, аватар, «о себе» | ✅ | Не влияют на обмен сообщениями |
| События (`MessagePosted`, `MemberJoined`…) | ✅ | Нет подписчиков |
| Редактирование/удаление сообщений | ✅ | Вне минимума |
| Постраничность/история с пагинацией | ⚠️ | history упрощается до «последние N сообщений» |
| `MemberRole` enum | ✅ | Не используется |

---

## 6. Оставшаяся ER-модель

```
users      ( id, username, password_hash )
chats      ( id, name, owner_id )
messages   ( id, chat_id, author_id, content, sent_at )
```

Таблицы `chat_members` и `outbox` — **удалены** (участие в чате можно хранить прямо в анкете или
просто считать, что все зарегистрированные видят чат; минимально — в `chats.owner_id`).

---

## 7. Многопоточность в MVP

Остаётся только **асинхронная обработка команд** (`async/await`), чтобы клиенты не блокировали друг друга.
Фоновые воркеры (outbox, хаб) не нужны.

---

## 8. Итог

**MVP-версия** — это полная архитектура, урезанная до:

> `ConsoleClient + ASP.NET Core (EF Core + PostgreSQL)` — без шины, микросервисов и ролей.

Этого достаточно, чтобы запустить чат, зарегистрироваться, создать чат и обмениваться сообщениями в консоли.
Всё вырезанное (брокер, микросервисы, роли, realtime) можно добавить позже, не меняя ядро модели — 
благодаря изначальному разделению на DDD-слои.
